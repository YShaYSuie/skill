# 每日复盘与日报（Daily Summary）

> `SKILL.md` 只描述主干：**读日志 → 统计 → AI 总结 → 生成日报 → TickTick 同步**。
> 本文档承载详细口径：数据源、统计维度、过滤与合并规则、日报格式、角色维度。

---

## 1. 一句话原则

> **日报只消费已经结算好的日志。** 每日复盘**不得**重新扫描 Raw Conversation，
> **不得**重新计算 Conversation Token / Skill Token / Score。

```text
✗ 错误：历史 Conversation → 复盘 → 重新解析 Skill / 重算 Token / 重算 Score
✓ 正确：对话结束 → 立即结算并落盘 → 复盘只做 sum / group / join
```

---

## 2. 数据源（固定为当天）

| 内容 | 数据源 | 说明 |
|---|---|---|
| 工作事项（几点做了什么） | `<log_dir>/current.json` | **唯一数据源**。不读 `pending/`，不做历史日期总结 |
| AI 使用（这次对话花了多少） | `<log_dir>/logs/<date>/{conversations,skill-usage,work-activities}.jsonl` | 由结算阶段写入，复盘只读 |
| 周期分析（7 / 30 天） | `<log_dir>/logs/**` | 走 `aggregate-logs.js --days N`，同样只读 `logs/` |

两者是**互补**关系，**不互相替代**：

```text
current.json.records   → 工作事项 —— 同步到滴答清单的**单位**
logs/<date>/*.jsonl    → 对话成本 —— 这次对话花了多少 / 用了哪些 Skill
```

**结构化日志缺失或损坏时**：日报主体照常产出，只在 AI 章节提示「不可用」。
**不得**因为拿不到 AI 汇总就去重扫历史对话。

> 显式传 `--date <YYYY-MM-DD>` 且与 `current.json` 的 `date` 不一致时，脚本**直接报错**，
> 而不是返回空结果 —— 避免用户误以为「那天没有工作记录」。

## 3. 两种产出：脚本草稿 与 AI 日报

### 3.1 脚本确定性草稿（`daily-summary.js draft`）

零 AI 调用。**V3.6 起 `draft` 默认输出「七段结构」**，面向「人能直接看」：

```text
1. 今日概览        —— 工作 / 探索沉淀 / 生活 **三线并出**（项数 + 时长）
2. 工作            —— **只含 category = 工作**，按【产品线/项目 → 项目阶段 → 交付物】组织
3. 探索沉淀        —— 优先展示 Skill / 工具的用户可感知能力变化；稳定性维护折叠计数
4. 今日成果        —— 只列真写了 `output` 的；没有就写明「未填写 —— 不虚构成果」
5. 生活与个人事项  —— 生活 / 运动 / 休闲 / 个人成长；**不做职业化解读**
6. 时间结构        —— 各分类时长 + 工作 / 探索沉淀 / 非工作合计；未记结束时间标注为「未计入时长」，合计标注为**下界**（V3.25）
7. AI 使用情况     —— 会话 Token / 积分 + 按 Skill / **模型** / 工作类型 / 项目 / 项目阶段
```

**V3.6 的两处关键调整（用户 2026-09-24）**：

```text
① 工作块换主轴 —— 从「工作类型分组 + 内容叙述」改为「交付物 / 阶段为主轴」。
   用户原话：「现在的总结都是我解决了什么问题……在工作上面，没有很体现我的实际工作内容。」
   因此每个产品线/项目先给**项目阶段分布**，再给**实际产出的交付物**
   （需求文档 / PRD / 原型 / 评审结论 …），事项内容只作明细行。
   原「4. 项目进展」并入第 2 段 —— 按项目组织即已含阶段分布，单列会让同一批事项出现两次。

② 探索沉淀独立成段 —— 「给 skill 加功能」这类事项不再混进工作块。
   `AI Skill 探索` 项目下的事项一律记「探索沉淀」，不参与阶段与交付物口径。
```

**V3.24（用户 2026-09-28）补充**：

```text
· 正式 /summary 与日报草稿共用同一套 work_board / exploration_updates；
  不再存在第二套 project_rollup 旧分类。
· 探索沉淀允许保存 output；只描述用户可感知的能力变化。
· 纯修复 / 稳定性维护折叠计数，不占主位。
· 查看日志、环境恢复、任务重跑、自动化结果属过程 / 维护活动；
  自动采集时默认不进主总结，手动记录与有明确 output 的事项除外。
```

原有的**明细草稿**（十一章式：时间线、项目统计、待确认事项、Skill 明细…）**没有删除**，
改用 `daily-summary.js draft --verbose` 取。

> 为什么改成七段：原十一章式把「工作 / 探索 / 生活」摊在同一维度上，
> 读起来像工程日报，也不回答「今天产出了什么」。七段结构按**读者关心的顺序**组织。

`--json` 时返回结构化视图（`category_breakdown` / `work_board` / `exploration_updates` /
`pm_work` / `projects` / `outputs` / `cost` / `models`），供 AI 组织语言，**不重算任何数字**。

### 3.1a AI 使用洞察（`daily-summary.js insights`，V3.6）

回答用户的四个问题：**哪个 Skill 高频 / 哪个用不上 / 哪个消耗偏高 / 哪个模型有用**，
外加「项目工作中哪个阶段更侧重在 AI 上」。

```bash
node scripts/daily-summary.js insights                 # 今天
node scripts/daily-summary.js insights --date 2026-09-23
node scripts/daily-summary.js insights week|month|project [--days N] [--from --to] [--project 名]
node scripts/daily-summary.js insights --save          # 落盘 summaries/<key>-insights.md
node scripts/daily-summary.js insights --json          # 结构化给下游
node scripts/daily-summary.js insights --recheck       # 对已确认的归属也重新复核
```

**章节与判据**：

| 章节 | 内容 | 判据（全部规则驱动、可复核） |
|---|---|---|
| 一 总览 | 会话 / 请求 / Token / 积分 / Agent 分布 | 会话级真实总量 |
| 二 Skill 盘点 | 高频、全部明细、装了没用过、长期未调用、清单外引用 | 高频 = 调用次数降序；用不上 = 已装未用 / `stale_days` 天未用 |
| 三 模型对比 | 会话 / 请求 / Token / 占比 / 缓存命中率 / 平均单请求 / 积分 | 按归一后的模型聚合；会话整体记给主模型 |
| 四 成本分布 | 工作口径的项目 / 阶段 / 工作类型 + 全量口径 + 精确归属 | 会话级范围口径；歧义不计入任何一方 |
| 五 项目阶段侧重 | 项目 → 阶段的 Token 分布 | 工作口径；跨阶段会话因歧义不计入 |
| 六 解读提示 | 告诉撰写环节该看哪张表 | 不产出数字 |
| 七 口径与限制 | 为什么某些值是 null、怎么补齐 | 归因覆盖率 + 精确归属为空的原因 |

```text
「消耗偏高」判据（两项同时成立，且调用 ≥3 次）：
  ① 载入体积（A 口径）高于同批中位数
  ② 平均单次调用所在请求用量（B 口径）高于同批中位数
  B 口径整体不可用时降级为单判据，并在报告里标明「已降级」。

⚠️ A/B 都不是真实消耗，报告里必须标注 —— 真实消耗无法精确归属到 Skill。
```

### 3.1b 周 / 月 / 项目总结（V3.3 新增）

```bash
node scripts/daily-summary.js week                        # 本周一 ~ 今天
node scripts/daily-summary.js week --days 7               # 近 7 天
node scripts/daily-summary.js week --from 2026-09-01 --to 2026-09-07
node scripts/daily-summary.js month                       # 本月
node scripts/daily-summary.js month --month 2026-09        # 指定月份
node scripts/daily-summary.js project --project 云浮门户   # 单项目全过程
```

**数据源不同（重要）**：

```text
draft（日）   → current.json（当天 WorkItem 记录）
week/month/project → logs/<date>/{work-activities,conversations,skill-usage}.jsonl
                     （已永久归档的结构化日志；未归档的日期不在统计范围内）
```

`project` 的日期范围默认取**该日志区间内最早 ~ 最晚**，可用 `--from` / `--to` 收窄。

四类周期报告共有的章节与各自的差异：

| 章节 | 日 | 周 | 月 | 项目 |
|---|---|---|---|---|
| 时间投入（分类 / 合计） | ✓ | ✓ | ✓ | ✓（项目口径） |
| 项目投入 | ✓ | ✓ | ✓ | — |
| 产品经理工作类型分布 | ✓ | ✓ | ✓ | ✓ |
| 项目阶段 | — | — | — | ✓ |
| 主要工作成果 | ✓ | ✓ | ✓ | ✓ |
| 生活 / 运动 / 个人成长 | ✓ | ✓ | ✓ | ✓ |
| AI 使用与成本 | ✓ | ✓ | ✓ | ✓ |

> ⚠️ **`project` 报告的会话级成本仍是区间口径。**
> 只有 AI Usage Record 精确归属到本项目的内容可以写成「本项目已归属消耗」；
> 会话级总量继续标注为「区间会话级消耗，不是仅本项目的消耗」。JSON 里会同时保留
> `cost_scope: 'range'`，并把精确归属放在 `allocated_by_project` / `usage_attribution`。

### 3.2 AI 日报（`/summary` 撰写后 `save`）

由 AI 在草稿/素材基础上撰写，**推荐章节结构**（以实际历史日报为准）：

```text
一、今日概览            —— 工作 / 探索沉淀 / 生活三线 + 实际占用时长
二、工作完成情况        —— 产品线 / 项目 → 项目阶段 → 交付物
三、探索沉淀            —— 优先写新增 / 调整 / 移除的能力；稳定性维护折叠计数
四、AI 协作摘要         —— AI 协助形成了哪些结果，不罗列操作轨迹
五、过程与维护          —— 日志查看、环境恢复、任务重跑等，默认折叠
六、AI 成本与洞察       —— Conversation / Token / Agent / Model / Skill / 项目阶段
七、待确认事项
八、口径说明            —— 本报告的口径与限制
```

`save` 写入 `<log_dir>/summaries/<date>.md`（**永久保留**）。

### 3.2a 日报过期检测（V3.27）

**问题**：日报只读**已结算**的结构化日志（正确，见 §8 硬规则），但落盘后就是静态文件。
此后新增的会话不会进入它，而文件本身没有任何标记 —— 人和 AI 都可能把旧日报当成当日全貌。

> **真实事故（2026-09-28）**：`summaries/2026-09-28.md` 停在 14:36，
> 当天 Conversation 已从 10 个涨到 25 个。下午的 PRD、需求分析、原型等工作
> 全部不在那份日报里，而读取者无从察觉。

**判定口径**（三条同时成立才算过期）：

| # | 条件 |
|---|---|
| 1 | `current.json.summary` 已存在（日报已落盘） |
| 2 | `generated_at` 早于**最后结算时间**（当日会话 `settled_at` 最大值） |
| 3 | 生成时间之后新增的 Conversation 数 ≥ 阈值（默认 **3**） |

**阈值配置**：`config.summary.stale_conversation_threshold`（缺省 3，非法值回退 3）。
> ⚠️ 该键已在 `normalizeConfig` 白名单中登记 —— 未登记的键会被静默丢弃，
> 用户写了也不生效。新增同类配置项时必须同步登记。

**行为约束**：

- **只报不改**：不触发重新生成、不写任何文件（有测试钉住「检测前后字节一致」）。
- **宁可漏报，不可误报**：缺时间戳、文件缺失、读取失败一律返回 `stale:false`。
  误报比漏报更糟 —— 会让人对所有 ⚠ 脱敏。
- **静态文件不写动态结论**：`summaries/<date>.md` 头部只写「数据截止」（= 生成时刻），
  **不写**「是否过期」。过期随时间变化，一旦写进静态文件就会立刻开始说谎。
- 呈现位置：`today` 与 `draft` 的文本输出首行；`--json` 输出 `summary_staleness` 字段。
- `--no-stale` 可关闭检测（脚本级，不写配置）。

**输出示例**：

```text
⚠️ 本日报数据截止于 2026-09-28 14:36:18，此后新增 21 个会话（最后结算 2026-09-28 18:02:40），建议重新生成。
```

### 3.3 三步编排（`/summary` 官方流程）

```bash
node scripts/export-work-activities.js              # ① 已归类事项导出为永久日志
node scripts/daily-summary.js material              # ② 取总结素材（已过滤 + 已合并 + AI 汇总）
#                                                   ③ AI 撰写
node scripts/daily-summary.js save --text "..." --trigger manual
```

> **素材入口不得隐藏素材**：`material` 与 `draft` **必须**共用同一套待判断事项渲染。
> 曾出现「只有 `draft` 展开内容、`material` 只给计数」，而 `/summary` 官方流程走的正是
> `material` —— 撰写环节于是**永远看不到那些内容**（真实事故）。

## 4. 过滤与合并（总结层，纯本地规则、零 Token）

**采集层不过滤，总结层才过滤。** 这是两层职责的分工：

```text
current.json.records          原始记录 —— 采集时不因「像闲聊」而丢弃
        ↓ buildSummaryView()  只读派生，绝不写回
   过滤无关对话  +  合并相关事项
        ↓
DailySummary / material / draft
```

实现：`scripts/lib/summary-engine.js`。

### 4.1 无关对话过滤

普通无关对话只对 **`source: auto`（宿主采集）且无项目/工作类型**的事项生效。
**过程 / 维护活动例外**：即使带项目名，只要没有明确 `output`，也不得因“有项目”而放行。
**用户手动记录的一律保留** —— 那是刻意记的。

高置信度噪声特征（`strict`，即使含工作词也过滤）：

```text
总结/汇总/复盘类操作指令     「总结今日」「总结一下」
点名同步目标的同步指令        「同步到滴答清单中」
关于记录工具本身的问答        「这个 hook 怎么配置啊」
查询类指令                   「看看今天的记录」
系统运行状态询问              「现在这个 skill 开始自动记录了吗」
过程 / 维护活动               「查看日志」「修复网络问题」「自动化任务结果」
```

低置信度特征（**含工作性词汇时保留**，防误杀）：疑问句 / 寒暄 / 闲聊 / 生活闲聊。

过程 / 维护活动只对**自动采集**生效：用户手动记录时视为刻意登记；
已填写明确 `output` 的事项也不算纯维护活动。

> ⚠️ **防误杀是重点**：「你好，帮我完善GPU需求」不应因寒暄开头被丢弃；
> 「现在开始设计容器创建页面」不应被系统状态规则吃掉；
> 「散步」「瑜伽」这类**短生活事项**不应被「内容过短」误杀。
> 为此引入 `WORK_KEYWORDS` 白名单，并以 `strict` 区分两类特征。
> **噪声必须由具体特征命中，不使用「内容过短」这类粗暴规则。**

**⚠️ 宿主系统通知必须独立于来源与项目判定**：`UserPromptSubmit` 通道会混入
`<task-notification>…` 这类通知，其内容可能含项目路径。一旦被赋了 `project_name`，
「有项目名即真实事项」的规则会让它**绕过噪声过滤**。因此 `classify()` 中
`HOST_NOTICE_RE` 判断必须放在放行规则**之前**。

### 4.2 相关事项合并（核心是「同一工作意图」）

```text
硬边界：
✗ 已确认属于不同 project_name → 不合并
✗ category 明确不同（如「工作」与「生活」）→ 不合并

合并证据按优先级：
① 同 segment_id
② 同 Conversation（conversation_id / session_id）且上下文续接
③ 同 project_name + 同模块
④ 同 project_name + 同 work_type + 内容相关
⑤ 跨 Conversation 但内容强相关（共同词 ≥ 3 或相似度 ≥ 0.5）
⑥ 同 project_name + 同 work_type + 时间紧接

仅凭「同工作类型」「同一天」「时间接近」不能合并。
```

**同一 Conversation 是强上下文证据，但不是自动合并条件。** 同一会话中，后一条是对
前一条的继续、补充、修正、验证或推进同一对象时，才允许合并。上下文信号包括：

```text
继续 / 接着 / 再 / 补充 / 改成 / 按照 / 这个 / 上述 / 刚才 / 前面 / 统一为
同一个页面、模块、需求、文档、问题或交付物
从设计到验证、从排查到修复、从需求到方案的动作连续性
前后 project_stage / output / 工作目标一致
```

同会话项目一致且时间连续时，可以使用上下文归并；出现“换个问题、先不说、转到另一个项目”
等明确主题切换，或者出现已确认的不同项目，必须拆分。

**同一模块的工作往往措辞差异很大**，只靠关键词相似会漏并，所以模块仍是重要证据。
模块名经**别名归一**（词表可用 `config.summary.module_keywords` /
`module_aliases` 扩展）：

```text
「邮箱配置」「邮箱服务」「邮件管理」  → 邮件与邮箱配置
「实验中心」「课程中心」「权限配置」  → 权限与中心管理
「门户导航」「原型导航」「首页」     → 导航与布局
「需求说明书」「需求规格」           → 需求文档
```

> 为什么需要别名：`在系统管理需要添加二级菜单：邮箱配置` 与
> `在邮件管理中需要提供是否开启邮箱服务` 是同一件事，但共同词只有 3 个泛词、相似度低
> —— **靠措辞判断会漏，靠模块判断才对**。

合并结果：

```text
start_time      取组内第一个时间，也就是最早时间
time_segments   取并集（相邻片段自动衔接）
actual_duration 按合并后片段重算
content         反选信息量最高的事项，必要时提炼为同一工作流摘要
                （排除「怎么解决」这类只有上下文、没有独立信息的短句）
status          全部完成 → completed；有进行中 → in_progress
merged_from     保留原始 id 列表（可追溯）
merged_titles   保留所有来源事项内容
merge_evidence  记录为什么合并（同 Segment / 同会话上下文 / 同模块 / 内容相关…）
```

**不同项目不合并**；**同一会话但主题已切换也不合并**。完整问答仍保留在原始记录中，
不进入合并后的事项正文，只作为溯源与复核证据。

### 4.3 ⚠️ 时间字段必须完整保留（合并后不得丢失）

```text
有 start + end  → 两者都保留      （完整时间段）
有 start 无 end → 保留 start      （归类后常无法确定结束时间，不编造）
无 start        → 保持为空        （不得凭空补时间）
```

两个数据来源都要覆盖，`start_time`/`end_time` 与 `time_segments` 必须**相互补全**：

| 来源 | 特征 | 风险 |
|---|---|---|
| `/log` 手动补录 | 只有 `start_time`/`end_time`，无 `time_segments` | 只认 segments 时 `end_time` 被丢弃 |
| 宿主自动采集 | 有 `time_segments`（可能末端未闭合） | 未闭合时 `end_time` 取不到 |

> **踩过的坑**：原实现 `start_time` 有回退、`end_time` 没有，导致
> 「散步 12:58-13:08」这类**明明有时间**的记录一旦被合并就丢失结束时间、时长归零。
> 已修正为**对称回退**（`fallbackSegments(rec)`）。

### 4.4 透明性

过滤结果只报**数量与原因**，**不回显对话内容**（避免再次进入 AI 上下文）：

```text
附：本次总结已排除的内容
  已过滤与工作事项无关的对话 4 条，原因为：
  - 无关对话：对记录工具的操作指令
  - 无关对话：关于系统运行状态的询问
  这些对话不在每日总结中体现，但仍原始保留在日志里可供追溯。
```

原始记录**永不被删改** —— AI 总结出错时仍可重新分析。

## 5. 输出格式：【项目名称】【功能/模块名称】事项内容

事项内容用 **模块 + 动作** 提炼成短语，不直接堆原始长句：

```text
原始：在系统管理需要添加二级菜单：邮箱配置，该页面主要是配置系统发件箱的授权信息…
标题：【气象数据】【邮件与邮箱配置】邮件与邮箱配置更新

原始：5.2 实体关系下的内容好像有点奇怪，怎么显示了Syntax error in text？
标题：【云浮门户】【实体关系】实体关系问题排查
```

**动作词表**（`ACTION_HINTS`，顺序敏感）：
需求分析 / 需求梳理 / 问题排查 / 更新 / 优化 / 设计 / 测试 / 开发 / 配置 / 梳理

**拼接去重**（`joinModuleAction()`）—— 否则会产出「系统配置配置」这类重复：

```text
系统配置 + 配置      → 系统配置          （动作已在模块名里）
需求文档 + 需求梳理  → 需求文档梳理       （去掉重复的「需求」）
方案编写 + 梳理      → 方案编写          （模块本身已是动宾结构）
```

**退化规则**（不编造）：

| 情况 | 输出 |
|---|---|
| 有项目 + 有模块 | `【项目】【模块】模块+动作` |
| 有项目、**识别不到模块** | `【项目】内容首句` ← **不显示模块块** |
| 无项目 + 有模块 | `【模块】模块+动作`（不编造项目名） |
| 既无项目也无模块 | 沿用原显示（生活事项等），不套任何标签 |

时间缺失时的展示：

```text
10:10-11:20   完整时间段
15:20-        仅有开始时间（结束时间未知）
（未记录）     无任何时间
```

**不得**用 `actual_duration` 反推时刻，也**不得**为凑齐时间段而编造 `end_time`。

**待判断事项按模块归并**展示，不逐条罗列：

```text
待判断事项（按项目与功能模块归并，共 14 条 → 11 项）：
- 【云浮门户 / 需求说明书】…  （共 2 条，最早 14:47）
- 【云浮门户 / 权限与中心管理】…（共 3 条，最早 15:26）
```

## 6. 角色维度汇总（日报第十章）

**同一份记录，不同角色关心的维度不同。** 事实层（`content` / 时间 / 项目）不变，
但**组织方式**要贴合用户职业。画像落在 `config.role`，用户可随时改，不需改代码：

```json
"role": {
  "title": "产品经理",
  "enabled": true,
  "stages": ["需求分析", "方案设计", "评审对齐", "跟进落地"],
  "deliverables": ["需求文档", "需求规格说明书", "原型", "评审结论", "竞品分析", "排期表"],
  "product_lines": [],
   "focus": ["需求阶段分布", "按产品线汇总", "交付物产出", "探索沉淀"]
}
```

- `enabled: false` → 完全退化为通用总结，不输出角色块。
- `stages` / `deliverables` 换成自己的词表即可 —— 识别**只认画像里声明过的词**。
- `product_lines` 留空表示「直接用记录里的项目名」。
- `focus` 决定三个维度的**排列顺序**。
- V3.6 新增第四个维度 `探索沉淀`：列出 AI 工具 / Skill / MCP / 提示词建设事项，
  与职业交付物严格分开（不计职业产出）。不写该维度时行为与 V3.5 一致。

输出示例：

```text
十、角色维度汇总（产品经理视角）
  角色相关事项 5 项 / 210 分钟

  · 需求阶段分布
      需求分析　2 项 / 120 分钟：梳理云浮门户需求说明书；做竞品分析
  · 按产品线汇总
      云浮门户　3 项 / 180 分钟
  · 交付物产出（产品工作）
      需求文档　×1
```

### 三条判定纪律

1. **只作用于 `category = 工作` 的事项** —— V3.3 起这条从「有项目名或有具体工作类型」
   收紧为**显式分类**（含推导结果）；分类未知时退回四分类（产品工作 / 其他工作算工作）。
   探索、学习、生活类单列一块，**不塞进职业维度**。
   > **生活 / 运动类不得被解释成职业产出。** 例如「普拉提课」不能写成
   > 「完成了身体状态维护」，也不能折算成任何工作成果。
2. **工具建设 / 探索沉淀单独剥离**（V3.6 起升级为独立**分类**）——
   为记录工具 / 自动化本身做的工作（含 `skill`/`hook`/`MCP`/`脚本` 等词）
   一律记 `category = 探索沉淀`，是**个人方向的沉淀而非职业产出**，
   单列成段并**不参与**阶段与交付物统计。
   > 真实踩到的坑：「创建**原型**版本发布 skill」因含「原型」被误判成「产出了原型交付物」。
   > 现在 `原型` 的识别要求**产出物语境**（原型设计/稿/图，或「画|做|出|更新了原型」）。
   > V3.6 更进一步：归属**优先级**改为「显式 category > 生活类强信号 > 项目归属 > 关键词」，
   > 项目挂在 `AI Skill 探索` 下的事项即使写着「需求分析」也不进工作块。
3. **识别不出就留空，不硬套** —— 阶段匹配不到记「未识别阶段」；
   交付物一个都没有就如实写「本日无产品工作，未产出角色交付物」。
   **不打印空壳块**。

### 产品经理工作类型分组（V3.3）

「产品工作」章节按**工作类型分组**组织，映射关系（未列出的类型进「其他」）：

| 分组 | 归入的工作类型 |
|---|---|
| 需求 | 需求分析、需求沟通、需求文档、竞品/行业研究、需求梳理、需求澄清 |
| 产品设计 | 产品规划、产品设计、原型设计、交互设计、UI设计 |
| 项目推进 | 上线发布、产品运营、产品复盘、会议、项目跟进、项目推进、版本发布、沟通协调 |
| 研发协作 | 研发协作、测试验收、问题处理、技术方案、开发、测试、问题排查 |
| 项目管理 | 项目管理 |
| 数据分析 | 数据分析 |
| 其他 | 其他工作，以及任何未列出的类型 |

```text
· 只输出**实际存在**的分组（不打印空块）
· 工作类型缺失时按内容兜底识别（仍属推导，**不写回记录**）
· 分组只覆盖 category = 工作 —— 生活 / 运动 / 休闲永不进入本表
```

纯本地规则、**零 Token**。改词表后必须重跑
`node scripts/test-role-profile.js` / `node scripts/test-summary-engine.js`。

## 8. 硬规则（写日报时不可违反）

```text
1. 不得重扫 Raw Conversation，不得重算 Token / Skill Token / Score。
2. 总结不得只看 records —— 采集到但未归类的事件都在 pending_items 里。
   ⚠ 待判断事项非空时，禁止对当日产出下排他性结论
   （如「无产品交付物产出」「全部为工具建设」）。
   2026-09-21 曾因此把 22 条真实产品工作（气象数据 17 + 云浮门户 5）整块漏掉。
3. material 与 draft 必须共用同一套待判断事项渲染（§3.3）。
4. 时长口径必须分两类并如实标注：
   「事项累计时长」与「实际占用时间」。
   **V3.25 起两者都是下界**：只累计人工明确记录的闭合时段 ——
   AI 会话推导的事项不产出时长（`duration_source = 'not_applicable_ai_session'`），
   未记结束时间的时段也不计入。**不得再写成「上界」**（那是「开放段按 now 兜底计价」
   的老口径，已废弃：它会让同一份历史数据换个时刻重算就变一个值）。
5. Token / Score 口径必须标注：
   - `skill_token` 是 A 口径载入体积，**不是**实际消耗；取不到显示「不可获取」。
   - `total_score` 覆盖不全时是**下界**，须一并说明覆盖率（`score_request_count`）。
   - Credit / 积分仅由积分类 Agent 产生；API 访问记 `not_applicable`，
     项目表中直接留空；真正的 `unavailable` 才表示宿主该报没报。
6. 工作日历归属用当日日期；`/today` 与 `/summary` 只针对当天。
7. TickTick 同步失败**不得影响**本地日志与日报产出（见 §9）。
8. **成果不得虚构**：`output` 为空就写「记录中未填写 output —— 不虚构成果」，
   不得用 `content` 反推一个「成果」。
9. **生活 / 运动 / 休闲 / 个人成长不得职业化解读**，也不得计入「工作」时长
   或产品经理工作类型分布（见 §6 纪律 1）。
10. **分类与项目阶段必须是 `config.work.*` 里的合法取值** —— 非法值在写入前被 CLI 拒绝；
    统计层遇到历史遗留的非法取值时**不丢数据**（排在已声明分类之后单独显示）。
11. 周期报告的**会话级成本仍是区间口径**；只有 AI Usage Record 精确归属到项目的内容
    才能表述为该项目消耗。两部分必须分栏显示，不得相加后写成项目总消耗。
12. `content` / `log` 的 200 字限制不适用于 `detail`；但 detail 仍必须脱敏并遵守
    独立安全上限，超过时按 `detail_compression` 留痕。
13. **日报落盘后必须能被识别出「数据截止到哪」**（V3.27）：
    读取历史日报前先看过期检测结论；⚠ 存在时，该日报**不得**被当作当日全貌使用
    （见 §3.2a）。静态文件里只写「数据截止」，不写「是否过期」。
```

## 9. 与 TickTick 的衔接

TickTick 属于**外部同步目标**，同步逻辑由 `ticktick-work-review` 承担。
本技能只负责**把事项与时间完整交出去**：

```text
已有未完成对应任务 → 匹配并完成
没有对应任务       → 创建并完成
避免重复创建（幂等）
```

**时间字段必须随同步交出**：

```text
有 start + end  → 两者都推送
有 start 无 end → 至少推送 start_time，不得因缺 end_time 而放弃推送
无 start        → 不推送时间
```

> 时间段必须落到 `startDate` / `dueDate` 且 `isAllDay = false`（`Asia/Shanghai`），
> 仅写进 `content` 文字不算推送时间。

**失败处理**：TickTick 同步失败**不得影响**本地日志、结构化日志与日报产出。
细节见 `references/ticktick-sync-contract.md`。
