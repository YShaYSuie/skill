# 工作分类与账本数据结构

本文件是 `ticktick-work-review` 的归类层参考，进行项目归属与工作类型判定时加载。

## 1. 工作类型（默认清单）

| 工作类型 | 典型内容 |
|---|---|
| 需求分析 | 需求澄清、需求评审、范围界定 |
| 产品方案 | 方案设计、功能设计、流程设计 |
| 原型设计 | Axure / Figma 原型制作与迭代 |
| UI/交互 | 界面设计、交互细节、视觉规范 |
| 需求文档 | PRD、SRS、规格说明书撰写 |
| 项目沟通 | 会议、对齐、跨部门协调 |
| 开发跟进 | 接口联调跟进、进度推动 |
| 测试验证 | 功能验收、用例执行、缺陷复现 |
| 问题处理 | 定位问题、排查缺陷、应急支持 |
| 数据分析 | 指标分析、数据核对、报表 |
| 技术调研 | 技术选型、方案比对 |
| 学习研究 | 学习新技术、研究行业方案 |
| 行政事务 | 报销、流程、内部事务 |
| 临时事项 | 临时插入的协助或响应 |
| 其他 | 无法归类 |

单一工作事项原则上只归一类；若确实跨类，取**占主导**的一类，不重复计数。

## 2. 项目维度

若能识别，项目必须保留。示例项目集：

```text
异构算力平台
校园物联网平台
虚拟仿真实验教学平台
个人效率
其他
```

规则：

- 项目名称**直接沿用 TickTick 中已有清单名**，不自造别名。
- 与 TickTick 清单无法对应的工作（如跨项目会议），归入「其他」或用户指定清单。
- **项目无法识别时不强行归类。** 宁可留在「未归类」，也不臆测归属。

## 3. 工作账本数据结构

### WorkLog（单项工作记录）

```text
WorkLog
├── 日期          例：2026-09-16
├── 项目          例：异构算力平台
├── 工作事项      例：完成设备总览页面设计
├── 工作类型      例：原型设计
├── 时间          例：14:00-15:00 / 15:20-（仅开始）/ 未记录
├── 来源          原任务 / 自动补录 / 用户补充
├── 对应 TickTick 任务   taskId + projectId + title（无对应任务才留空）
├── 完成状态      FULLY_COMPLETED / PARTIALLY_COMPLETED / ...
└── 证据          用户描述原文 / 已完成任务记录 / 专注记录
```

### 「时间」字段的两条约定

1. **实况填写，不留空不编造**：`14:00-15:00`（完整段）/ `15:20-`（结束时间未知）/
   `未记录`（无任何依据）。归类合并后常无法确定结束时间，此时保留开始时间即可。
2. **结束时间按来源处理**：
   - AI 对话推导事项：只把 `start_time` 写入 `startDate`，会话结束时间不写
     `dueDate`，也不宣称为真实结束时间。
   - 手动录入事项：明确填写的 `start_time` / `end_time` 分别写入
     `startDate` / `dueDate`，完整区间写入 `content`。
   细则见 `references/mcp-capabilities.md` 的「时间字段默认映射」。

### 「对应 TickTick 任务」必须回写 `taskId`

同步产生 / 更新任务后，把 `taskId`（与 `projectId`）回填到此字段，形如：

```jsonc
"ticktick": { "taskId": "...", "projectId": "...", "syncedAt": "<ISO 8601>" }
```

本地日志此前不保存 `taskId`，导致每次同步只能靠标题搜索匹配；
标题一旦不一致（如本地 `考核模块状态机设计` ↔ 滴答 `【粤企知】考核模块状态机设计`）
就会失手改错任务。回写后即可按 `taskId` 精确定位。参见 `mcp-capabilities.md` 的「taskId 回写约定」。

核对关系：

> TickTick 任务 = 行动管理
> WorkLog = 实际工作记录

### DayLog（每日账本）

```text
DayLog
│
├── CompletedTasks
│   ├── Existing      原有任务中完成的
│   └── New           AI 自动补录并完成的
│
├── PartialTasks      部分完成任务
├── UnfinishedTasks   未完成任务
├── WorkItems         全部工作事项（含未对应任务的工作）
├── Projects          涉及项目
├── Categories        工作类型分布
├── TimeDistribution  时间分布
└── NextActions       下一步行动建议
```

## 4. 补录率指标

本 Skill 区别于普通 AI 复盘的核心里程碑指标：

```text
实际完成且已有 TickTick 记录  +  实际完成后由 AI 自动补录
```

目标：尽可能让实际完成的工作都得到记录。

示例：

```text
今天实际完成工作：8 项
原 TickTick 已记录：5 项
AI 自动补录：3 项
最终工作记录：8 项
```

输出时在日复盘的「补录情况」段落呈现该三行对照即可，**不对补录率做优劣评价**。

## 5. 计数的边界

**不追求完成任务数量。** 计数仅用于事实呈现：

- 一项复杂工作即使内部包含多个子环节，也按 1 项计（除非原本就是独立工作）。
- 不为了增加完成数而拆分已完成任务。
- 补录计数以「工作事件」为单位，不以操作步骤为单位。

## 6. 涉及的另一套系统：下一步

复盘结束后识别的「下一步行动」是**建议**，默认不落入 TickTick。

只有在用户明确授权（「帮我把下一步拆成 TickTick 任务」）时，才按以下路径落库：

```text
NextAction
  ↓ 用户授权
create_task（放入对应项目清单，设置 dueDate）
  ↓
回到 TickTick 任务系统 → 下一轮复盘的判定输入
```

这构成完整闭环：

```text
用户想法 → TickTick（任务记录）→ AI 工作 Agent（计划 / 执行 / 复盘）
        → 工作账本 → 日/周/月复盘 → 下一步行动 → 新的计划
```
