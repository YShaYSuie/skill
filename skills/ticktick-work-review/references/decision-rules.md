# 判定规则细则

本文件是 `ticktick-work-review` 的判定核心，执行任务匹配、状态判定、补录判定与时间统计前加载。

## 1. 实际工作优先原则

必须严格区分三层：

| 层 | 含义 | 来源 |
|---|---|---|
| A 计划做什么 | 原始意图 | TickTick 任务 |
| B 实际做了什么 | 真实发生的工作 | 用户描述、已完成任务、专注记录、日程 |
| C 最终记录什么 | 综合判断后的账本 | Skill 综合 A + B 判定 |

两条推论：

> **TickTick 未完成 ≠ 用户没有做。**
> **用户说做过 ≠ 原 TickTick 任务已完整完成。**

## 2. 任务匹配算法

匹配输入信号（综合加权，非单一维度）：

```text
标题 + 语义 + 项目 + 清单 + 描述 + 日期 + 用户上下文
```

**核心原则：完成证据优先于标题相似度。**

即：一个标题相似度 0.9 但无任何完成证据的任务，其判定优先级**低于**标题相似度 0.6 但用户明确说「已完成」且时间吻合的任务。

匹配决策顺序：

1. 用户描述中是否含与任务标题明显重合的关键词（项目名、模块名、动作）？
2. 时间是否吻合（用户说"上午做的"vs 任务 dueDate 为上午）？
3. 项目是否吻合？
4. 任务范围是否被用户描述覆盖？

四项中命中 ≥2 项且无冲突证据 → 视为匹配。

## 3. 五种完成状态判定

| 状态 | 判定条件 | 操作 |
|---|---|---|
| `FULLY_COMPLETED` | 有明确任务 + 用户明确完成 + 实际工作覆盖任务范围 + 没有明显剩余工作 | 自动 `complete_task` |
| `PARTIALLY_COMPLETED` | 有明确任务 + 用户完成了其中**一部分**，或描述中显式留下未完成部分 | 不完成，列入部分完成并写明剩余 |
| `NEW_COMPLETED_WORK` | 用户实际完成了工作，但 TickTick 中**无对应任务** | 查重后 `create_task` + `complete_task` |
| `UNCERTAIN` | 存在匹配任务，但完成证据不足，或范围覆盖不确定 | 不修改，列入「待确认」并询问用户 |
| `ALREADY_COMPLETED` | 任务在今日完成列表中已存在 | 不操作 |

### FULLY_COMPLETED 四条件缺一不可

任一条件不成立 → 降级为 `PARTIALLY_COMPLETED` 或 `UNCERTAIN`。

典型反例：

- 任务「完成 GPU 细粒度调度设计」，用户说"今天把 MIG 模式做完了" → **PARTIALLY_COMPLETED**（还有显存隔离、节点选择未做）。
- 任务「整理需求文档」，用户说"写完了前半部分" → **PARTIALLY_COMPLETED**。
- 任务「调研 AI Agent 应用」已存在，用户只说"看了点资料" → **UNCERTAIN**（无法判断覆盖范围）。

## 4. 补录判定

### 可以补录的三个条件（同时满足）

```text
实际发生 + 对工作有意义 + TickTick 没有记录
```

### 允许补录的粒度示例

- 与开发确认一个接口参数
- 回复一个关键项目问题
- 参加一次需求讨论
- 修正一处原型
- 临时定位一个问题
- 整理一份资料

「小而有意义」即可记录——这与滴答清单「快速捕捉 → 后续整理」的设计思路一致：收集箱存在的意义就是降低记录成本，避免临时事项被遗漏。

### 禁止补录的行为（碎片任务污染）

- 打开文档
- 查看一封普通邮件
- 喝水
- 单纯查看页面
- 普通聊天
- 没有产生实际工作成果的操作

判定标尺：

> **记录「有工作意义的事件」，而不是记录所有行为。**

### 粒度原则：工作事件优先，而非操作步骤

| 用户描述 | 正确补录 | 错误补录 |
|---|---|---|
| 做完设备总览页面 | 完成设备总览页面设计（1 条） | 打开 Axure / 修改页面 / 修改表格 / 调整布局 / 保存原型（5 条） |
| 和开发开了个会 | 参加项目开发对齐会（1 条） | 打开会议软件 / 发言 / 记录 / 关闭（4 条） |

## 5. 补录前查重规则

必须执行 `search_task`，判重维度：

1. **标题相似**：核心词重合度高的任务
2. **同项目重复**：同一清单内语义重复
3. **已完成任务重复创建**：今日已完成列表中已有相同工作
4. **多份相同任务**：存在 2 个以上表述一致的任务

命中任一 → 不创建新任务；若是「重复任务」本身的问题，归入 MODE_TASK_CLEANUP 报告。

## 6. 任务拆解判定

任务「过大」的信号：

- 标题含「整体」「全部」「完整」等笼统词
- 预估涉及多个子系统
- 已有多次延期历史
- 完成标准无法一句话说清

拆解建议示例：

> 「完成异构算力平台整体设计」可建议拆为：

```text
1. 梳理 GPU 资源模型
2. 设计 GPU 分配配置
3. 设计容器创建交互
4. 设计节点资源调度
5. 整理完整需求规格说明书
```

**默认只建议，不自动拆分。** 仅当用户明确说「帮我拆成 TickTick 任务」才执行。

## 7. 模糊任务判定与改写

判定信号：缺少动作动词、缺少对象、范围无法界定。

| 原任务 | 建议改写 | 原因 |
|---|---|---|
| AI | 调研 AI Agent 在产品工作中的应用 | 行动对象不明确 |
| API | 梳理 API 配置平台接口规范 | 缺少动作 |
| 看一下项目 | 检查项目当前开发进度 | 行动不明确 |

**默认不直接修改原任务。** 仅在用户授权后修改。

## 8. 时间统计规则

铁律：

> **事实优先，推断其次，不允许虚构。**

时间来源优先级：

1. 用户明确给出的时间（"上午 2 小时"）
2. TickTick 任务的时间字段
3. 专注记录（Focus）
4. 日程（Calendar）
5. 用户描述的时间范围（"下午做的"→ 只能记为「下午」，不可折算为具体小时）
6. 合理推断（需标注为推断）

**无任何数据来源 → 记「未记录」，不得编造。**

### 时间字段默认映射

开始时间必须结构化；`end_time` 是否落到 `dueDate` 取决于时间来源：

| 本地口径 | TickTick 字段 | 规则 |
|---|---|---|
| `start_time` | `startDate` | 有值即必须写 |
| AI 对话推导的 `end_time` | 不映射 | 只是会话收尾，不写 `dueDate` |
| 手动明确 `end_time` | `dueDate` | 写入明确结束时间，完整区间同时写 `content` |
| 独立真实截止时间 | `dueDate` | 与手动结束时间冲突时先确认 |
| — | `isAllDay` | 有具体开始时间时必须 `false` |
| — | `timeZone` | `Asia/Shanghai` |

- **开始时间必须写 `startDate`**。
- **AI 推导的结束时间不写 `dueDate`**；手动明确结束时间可写 `dueDate`。
- **只有 `start_time` 时只写 `startDate`**，`dueDate` 留空。
- **无时间时保持全天态**（`isAllDay: true`），不得凭空造时刻（呼应本节铁律）。
- 归类合并后常无法确定结束时间 —— 保留开始时间，`dueDate` 留空。
- **结束时间是否写备注，仍按来源**：只有手动明确录入的结束时间，才把完整区间复述进 `content`；
  AI 推导的结束时间是会话收尾，**既不写字段、也不写备注**。
  （模板与禁写清单见 `references/mcp-capabilities.md`「`content`（备注）模板」）

细则与正误 JSON 对照见 `references/mcp-capabilities.md` 的「时间段写入规范」。

### 时间投入分析的表述边界

| 允许 | 禁止 |
|---|---|
| 本月记录时间最多的项目是 A，共 20 小时 | A 是你最重要的项目 |
| 项目 A 投入 20h，完成 12 项，新增 4 项，3 项未完成 | 项目 A 投入产出低 |
| 该项目本月记录时间占比约 40% | 你应该减少投入 A 的时间 |

投入产出对照允许呈现，**结论性评价不可自动生成**，除非用户明确要求进一步分析。

## 9. 长期积压任务判定

检查信号：

- 长时间未完成（超过阈值，默认 30 天）
- 多次延期（历史 dueDate 被反复推后）
- 长期没有更新（无 content 变更、无子项勾选）
- 与当前项目明显失去关联

每项任务**只能给出以下建议之一**：

```text
保留 / 拆分 / 延期 / 归档 / 删除
```

**默认不直接删除任务。** 删除需用户明确授权。

## 10. 安全边界汇总

| 操作 | 默认 | 需用户明确授权后 |
|---|---|---|
| 完成明确完成的任务 | ✅ 自动 | — |
| 创建并完成明确完成的新工作 | ✅ 自动 | — |
| **写入开始时间与时间来源**（`startDate` / `content` / `isAllDay`） | ✅ 自动 | — |
| **写入手动明确结束时间或真实截止时间**（`dueDate`） | ✅ 自动 | — |
| **回写 `taskId` 到本地 WorkItem** | ✅ 自动 | — |
| 修改任务标题 | ❌ | ✅ |
| 修改日期 / 优先级 / 清单 | ❌ | ✅ |
| 拆分任务 | ❌ | ✅ |
| 归档任务 | ❌ | ✅ |
| **删除任务** | ❌ | ✅（绝对红线，无授权绝不执行） |
| 大规模重新规划 | ❌ | ✅ |

授权扩权后仍须遵守：**每一步都不破坏原始信息。**

### 时间字段写入为何属于「自动允许」

给已有任务补写 / 修正**本次记录到的开始时间与完整区间**，是在把用户提供的真实事实落位，
属于「准确反映真实工作」的核心动作，与「修改日期」性质不同：

- **自动允许**：把开始时间写进 `startDate`；AI 推导事项不写结束时间。
- **自动允许**：手动明确录入的结束时间、或用户明确给出的真实截止时间，写入 `dueDate`。
- **需授权**：改变任务的**计划日期**（把 dueDate 从明天挪到下周）、调整优先级、改写标题、迁移清单。
- **实测依据**：对 `status: 2` 的已完成任务写入时间字段后，`status` 与 `completedTime` 均不受影响，
  因此补写历史开始时间与手动明确结束时间是安全的、可逆的。

判定分界口诀：**「补写已发生的时刻」自动做；「改计划安排」先问用户。**
