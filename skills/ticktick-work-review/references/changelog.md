# 版本变更记录（changelog）

> 本文档承载 `ticktick-work-review` 的版本演进历史。**AI 执行任务时不需要读它** ——
> 只在需要追溯「某个口径为什么是这样」时查阅。
>
> **版本口径**：
> - 本技能**当前版本为 V1.2**，与 `SKILL.md` frontmatter 的 `version` 字段一致；改行为必须同时改这两处。
> - 采用**两段式编号**（`1.0` → `1.1` → `1.2`），与同族的 `work-time-tracking` 风格一致，
>   但**各自独立编号、不强行对齐** —— 两个技能由不同职责驱动，强行同步版本号只会制造无意义的耦合。
> - 条目次序为**日期为主序（新→旧）、同日内按版本号降序**。
> - **跨技能改动**（同时改了 `work-time-tracking` 的口径）须在本文件注明，并在对方 `changelog.md` 留一条对应记录。
> - `V1.0` 是**编号起点**，不追认此前未记录的逐次演进；它只把建立编号时已知的既成口径固定下来。

## V1.2 —— 补齐备注模板缺口：手动录入但结束未记录（2026-09-28）

**背景**：V1.1 把 `content` 定成「三种来源各有唯一模板」。回头核对真实数据时发现
**「手动录入 + 仅开始时间」没有可依的模板** —— 例如 `【example-project】【项目会议】商务沟通会议`，
用户明确给了开始时刻 `10:00`、未给结束时间：

```text
按 manual 写 → 缺「实际时间：HH:MM-HH:MM」行 → validate-content.js 必然判违规
按 none   写 → 只能写「（时间未记录）」→ 谎称没有时间，而开始时刻明明是事实
```

**变更**：

| # | 变更 | 说明 |
|---|---|---|
| 1 | 新增第 4 种来源 `manual_open` | 模板 `开始时间：HH:MM` ↵ `来源：WorkTimeLog <id>（手动录入）`；行数 2 行 |
| 2 | `validate-content.js` 扩展 | `SOURCES` 增 `manual_open`；`REQUIRED_LINE` / `EXPECTED_LINES` 同步；区间仍被 `interval` 规则禁止（该规则只对 `manual` 放行） |
| 3 | 模板错误提示精确化 | 违规提示改为按来源取模板样例（新增 `TIME_LINE_EXAMPLE`），不再写死 ai / manual 两种 |
| 4 | 自检用例 | 新增「合规：只写开始时间」与「违规：写了区间」两例（13/13 通过） |
| 5 | 文档 | `mcp-capabilities.md`「四种来源各有唯一模板」+ 第 3 种模板行 + JSON 示例 |

**不变**：`manual_open` 与 `ai` 的**时间行同形**（都只写开始时刻），区别只在来源标签 ——
标签仍如实写「手动录入」，不得因为「长得像 AI 推导」就改成 AI 推导。

**验证**：`validate-content.js --selftest` 13/13；真实数据 6 条已同步事项的备注全部 PASS。

## V1.1 —— 备注（`content`）模板补全 + 校验落地（2026-09-28）

**背景（用户原话）**：推到滴答清单的事项备注里出现了
`开始时间：11:30` 与 `本地区间：11:30-11:42；结束时间为会话收尾，非真实结束`，
用户质疑后一行「好像没啥用」。

**问题定位**：

1. **该行不是模板产物**。全库检索 `work-time-tracking` 与 `ticktick-work-review`，
   `本地区间` 这一措辞在两份技能中**均不存在** —— 它是同步时模型为「把信息写全」而自行拼出来的。
2. **根因是口径互斥**。同一技能内同时存在：
   - 「完整时间段写进 `content`」（`SKILL.md` §⑩、§6，无条件）；
   - 「AI 推导的 `end_time` 仅保留本地时间线」（`SKILL.md`、`mcp-capabilities.md`）。
   同时照做的唯一产物，就是「写上区间 + 补一句它不是真的」。
3. **模板欠定义**。此前只给 `content` 示例、不给禁写清单 —— 经验上，
   模板欠定义时模型一定会即兴发挥。

**变更**：

| # | 变更 | 说明 |
|---|---|---|
| 1 | 新增「`content`（备注）模板（强制）」 | `mcp-capabilities.md`：三种来源唯一模板（AI 推导 2 行 / 手动录入 2 行 / 无时间 1 行） |
| 2 | 新增**禁写清单** | AI 推导的区间、免责声明 / 自我解释、内部术语（`本地区间`、`本地时间线`）、TickTick 字段名（`startDate`）、映射箭头（`→`）、实现过程说明 |
| 3 | 澄清边界口径 | 备注只承载「字段装不下、**且可信**」的信息 + 来源锚点；不可信的时间只进本地日志字段 |
| 4 | 修正三处互斥口径 | `SKILL.md` §1⑩ / §⑩ / §6「完整区间写 content」→ 按来源限定；`decision-rules.md`「结束时间仍只写 `content`」→ 按来源区分；`mcp-capabilities.md`「会话结束时间只留在本地 `content`」→ 只保留在本地日志字段 |
| 5 | 新增校验器 | `scripts/validate-content.js`（零依赖）：`--source ai\|manual\|none --content "<文本>" [--workitem-id <id>] [--json]`，退出码 `0/1/2`；`--selftest` 含 11 个用例 |
| 6 | 校验接入流程 | 写入前构造 + 校验，回读后再校验；接入 `SKILL.md` 核心资源 / §1 步骤⑧ / 回读段 / §6 / §7 原则 16 / §8 反模式 / §9 异常表、`mcp-capabilities.md` 补录动作序列与常见失败表、`output-templates.md` 同步清单 |
| 7 | 违规处置规则 | 一律 `update_task` **只改 `content`**（不碰 `status` 与时间字段）后回读核对；无法重写则列「备注待修正」，**不得宣称同步完全成功** |

**跨技能改动（已同步对方 changelog V3.24.1）**：
`work-time-tracking/references/ticktick-sync-contract.md` §5.3 的「AI 推导 `end_time` 不得写 `dueDate`」
追加「也不得写进备注（`content`）」—— 该文件是 AI 推导结束时间的**语义定义处**，
不在此处封口，同一处漂移会从另一侧重新长回来。

**脚本自查踩坑（记录以免重犯）**：来源锚点正则以 `\S+` 捕获 id，会把前缀为全角括号的后缀
「（AI 推导）」一并吞进 id（全角括号不是空白字符），导致误报 `source-mismatch`；
改为 `[A-Za-z0-9-]+` 后修正。

**兼容性**：不改变任务创建 / 完成 / `taskId` 回写等任何既有行为；
仅收敛 `content` 的写法，并要求对既有不符模板的备注做「只改 `content`」的修正。
历史备注不强制批量返修 —— 下次同步该事项时顺带修正即可。

## V1.0 —— 版本编号起点：已知口径基线（2026-09-28）

本节**不追认**此前的逐次演进，只把建立编号时（2026-09-28）已成立的关键口径固定下来，
供后续追溯「为什么是这样」。以下均为**实测结论**，不是设计推断。

**职责分界**

- 事项的生成与提取 → `work-time-tracking`；滴答清单的同步逻辑 → 本技能。
- 分界口诀：「拿这份数据去滴答里怎么落、落到哪个字段」归本技能；
  「这份数据从哪来、怎么算出来」归对方。两边的 references 各写自己那一半，需要对面细节时读对方的文件，不复制。

**实测结论（按日期）**

| 日期 | 结论 | 影响 |
|---|---|---|
| 2026-09-16 | `create_task` 传 `status: 2` 不生效，返回仍为 `status: 0` | 统一改用「创建 → `complete_task`」两步法 |
| 2026-09-18 | `list_undone_tasks_by_date` **会漏任务**（同日同格式的另一条正常返回，目标条缺失） | 该接口不可作为区间内任务的完整枚举依据；已知任务须 `get_task_in_project` 逐个核对 |
| 2026-09-21 | 对 `status: 2` 的已完成任务补写 `startDate` / `isAllDay`，`status` 与 `completedTime` **均不受影响** | 「补写已发生的时刻」安全、可逆，故归入自动允许 |
| 2026-09-21 | 本地 WorkItem 新增 `ticktick` 字段，保存 `taskId` / `projectId` / `syncedAt` | 消除「只靠标题搜索匹配」的改错风险；无 `taskId` 时回退标题匹配 + 来源锚点核对 |
| 2026-09-28 | `create_task` 未传 `dueDate` 时，返回体与回读均显示 `dueDate == startDate`（系统自动镜像） | 「AI 推导事项 `dueDate` 留空」在落库层面往往做不到，交接侧不得据此判定同步失败 |
| 2026-09-28 | `update_task` **无法清空** `dueDate` —— 传 `1970-01-01T00:00:00.000+0000` 与传 `null` 均为 no-op，而同一接口改 `content` 正常生效 | 落库时不要宣称「`dueDate` 已留空」；会话结束时间不进任何 TickTick 字段 |
| 2026-09-28 | `search_task` 存在**索引延迟**：刚创建的任务同样搜不到 | 查重与核对新建任务改用 `get_project_with_undone_tasks` / `get_task_in_project`；不得因搜索为空就重复创建 |

**长期不变的判定与边界**

- 完成判定四条件缺一不可（明确任务 + 明确完成 + 覆盖范围 + 无明显剩余工作），否则降级。
- 补录三条件：实际发生 + 对工作有意义 + TickTick 没有记录；碎片行为不建任务。
- 时间铁律：**事实优先，推断其次，不允许虚构**；无依据写「未记录」。
- 删除是**绝对红线**：无用户明确授权绝不执行。
- 任务系统健康度只输出问题清单，禁止输出评分。
