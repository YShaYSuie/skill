# TickTick 每日工作复盘（TickTick Work Review）

## Overview

将滴答清单从「待办清单」扩展为「任务系统 + 工作账本」：既记录「准备做什么」，也记录「实际做过什么」。

核心闭环：

```text
记录 → 整理 → 执行 → 补录 → 完成 → 复盘 → 计划
```

本 Skill 的定位是**持续维护个人工作任务系统的 Agent**，而非一次性生成日报的工具。最大价值在于「实际工作补录」——让用户真正做过但忘记记录的工作，自动进入任务系统。

## 核心资源

- `references/mcp-capabilities.md` — 滴答清单 MCP 工具的调用契约、参数要点与调用顺序，执行任何 MCP 操作前按需加载。
- `references/decision-rules.md` — 任务匹配、完成状态判定、补录判定、时间统计、安全边界的完整判定细则，执行判定逻辑前加载。
- `references/output-templates.md` — 五种模式的标准输出模板（日复盘 / 今日计划 / 任务整理 / 周期复盘 / 下一步），生成输出前加载。
- `references/work-taxonomy.md` — 工作类型清单、项目维度与工作账本数据结构，归类时加载。
- `scripts/validate-content.js` — **备注（`content`）模板校验器**。写入前与回读后各跑一次：
  `node scripts/validate-content.js --source ai|manual|manual_open|none --content "<文本>" [--workitem-id <id>]`，
  退出码 `1` 即有违规；`--selftest` 自查（11 个内置用例）。规则与
  `references/mcp-capabilities.md`「`content`（备注）模板」**同源，改一处必须同步改另一处**。
- `references/changelog.md` — **版本变更史**（不是执行必需）。只在追溯「某个口径为什么是这样」时查阅。
  本技能当前版本 **V1.1**，与 frontmatter 的 `version` 字段一致；**改行为必须同时改这两处**。
  与 `work-time-tracking` 各自独立编号（`1.0 → 1.1`），不强行对齐；跨技能改动需在双方 changelog 各留一条。

## 与 `work-time-tracking` 的职责分界

两个技能共同维护同一套工作账本，分界线是一句话：

```text
事项的生成与提取   → work-time-tracking
滴答清单的同步逻辑 → 本技能
```

| 归本技能（同步逻辑） | 归 `work-time-tracking`（事项生成与提取） |
|---|---|
| Task 创建 / 更新 / 完成 | 活动采集、WorkItem 生成 |
| **本地字段 → TickTick 字段的映射** | 项目 / 工作类型推断、合并归类 |
| 幂等、`taskId` 产生与回写 | `display_content` 生成、`start_time`/`end_time` 计算 |
| 写入的授权分界（哪些自动、哪些需授权） | `time_unknown` 判定、交接 JSON 产出 |
| 按 `taskId` 或标题定位任务 | 本地 `sync.status` 状态机与 `/sync` 阶段流转 |

判断口诀：**「拿这份数据去滴答里怎么落、落到哪个字段」是本技能；「这份数据从哪来、怎么算出来」是对方。**

因此本技能**不重复定义**事项如何采集与归类；`work-time-tracking` 也**不过问**字段映射细节。
双方各自的 references 只写自己那一半，需要对面细节时**读对方的文件**，不复制。

## 工作模式路由

| 模式 | 触发语 | 章节 |
|---|---|---|
| MODE_DAILY_REVIEW | 复盘今天 / 总结今天 / 今天做了什么 / 帮我同步今天工作 | §1 |
| MODE_DAILY_PLAN | 今天做什么 / 帮我安排今天 / 帮我规划今天 / 今天有哪些重要任务 | §2 |
| MODE_TASK_CLEANUP | 帮我整理 TickTick / 整理一下任务 / 清理收集箱 / 有哪些任务需要处理 | §3 |
| MODE_PERIOD_REVIEW | 总结本周 / 复盘本周 / 看看这个月做了什么 / 分析最近一个月时间投入 | §4 |
| MODE_NEXT_ACTION | 明天做什么 / 下周做什么 / 帮我整理下一步 / 哪些任务应该继续推进 | §5 |

若用户表述同时命中多个模式（如"复盘今天，再看看明天做什么"），先执行 MODE_DAILY_REVIEW，再在同一轮追加 MODE_NEXT_ACTION 的「明日待处理」段落。

## 通用前置步骤

任何模式开始前：

1. 确定目标日期（默认今天；周期复盘按自然周 / 自然月）。
2. 若用户本次描述了实际工作，先完整读取用户描述，不急于调用 MCP。
3. 按模式执行对应流程；涉及写操作时严格遵守 §6 的授权边界。
4. 结束时按 §6 输出「本次 TickTick 同步」清单。

## §1 MODE_DAILY_REVIEW（每日工作复盘，核心能力）

用户说「复盘今天。」时必须完整执行以下 12 步：

```text
① 查任务        读取今日未完成任务
② 查完成        读取今日已完成任务明细
③ 识别实际工作  拆解用户本次口述
④ 匹配已有任务  按 references/decision-rules.md 的匹配规则
⑤ 完成明确任务  FULLY_COMPLETED → complete_task
⑥ 补录遗漏工作  NEW_COMPLETED_WORK → search_task 查重
⑦ 完成新增任务  create_task 后立即 complete_task
⑧ 验证同步      回读校验（含时间字段与备注模板），禁止假装成功
⑨ 汇总工作      按项目 / 工作类型归类
⑩ 汇总并落位时间 事实优先，无依据则写「未记录」；开始写 startDate；备注按 `content` 模板写（见下）
⑪ 输出未完成    含部分完成任务
⑫ 输出下一步    明日待处理建议，不自动改 TickTick
```

关键前置动作：若用户尚未描述实际工作（只说"复盘今天"），**先询问「今天做了什么」**再执行 ③——实际工作识别依赖用户输入，不可凭空推断。

### ⑩ 时间必须同时「汇总」和「落位」

时间处理有两个动作：

```text
汇总：把时间段算出来，写进复盘输出（时间线、时间列）
落位：开始时间写进 TickTick 的 startDate；备注按 `content` 模板写（手动明确才写区间，AI 推导不写区间）
```

**结束时间按来源区分：**

- AI 对话推导的事项：`end_time` 是对话结束或记录收尾时间，**不是真实结束时间**，
  只同步 `start_time`，不写 `dueDate`。
- 手动录入且明确填写结束时间的事项：该结束时间视为事实，可同步完整时间段。
- AI 推导事项只有在用户后续明确确认真实结束时间后，才可按手动明确时间处理。

| 情形 | 时间字段写法 |
|---|---|
| AI 推导，有开始 + 结束 | 只写 `startDate`；`dueDate` 留空；不要把对话结束写成实际结束 |
| 手动录入，有开始 + 结束 | `startDate` 写开始；`dueDate` 写明确结束；完整区间写进 `content` |
| AI 推导，只有开始 | 只写 `startDate`，`dueDate` 留空 |
| 同时有手动结束时间与独立截止时间 | 两者冲突时先确认 `dueDate` 代表哪一个，不得静默覆盖 |
| 无任何时间 | 保持全天态，不得凭空造时刻 |

复盘输出中时间列按实况展示：`10:10-11:20` / `15:20-`（仅开始）/ `（未记录）`。

每次同步后**必须回读** `get_task_in_project`，确认 `startDate` / `isAllDay` / `timeZone`
已按规则落地；AI 推导事项还要确认 `dueDate` 为空，手动明确时间段则确认 `dueDate` 与结束时间一致。
时间写漏是**静默失败**，不报错但记录不准确，只核对「任务存在」不算验证通过。

**备注（`content`）同样必须校验**：写入前先按模板构造，写入后回读核对。模板与禁写清单见
`references/mcp-capabilities.md`「`content`（备注）模板」，校验方式优先用
`scripts/validate-content.js`（`--source ai|manual|manual_open|none --content "..." --workitem-id <id>`，
退出码 1 即有违规）。备注里出现模板之外的行（如「本地区间：11:30-11:42」这类即兴发挥）、
或缺少 `来源：WorkTimeLog <本地 id>` 锚点，都算**未通过**，须用 `update_task` 只改 `content` 重写。

核对时**必须先确认任务身份**：有 `ticktick.taskId` 时按 id 定位；只能标题搜索时，
回读 `content` 中的 `来源：WorkTimeLog WI-xxx` 与本地 WorkItem id 对齐，**宁可不动，不可改错**。

实际工作识别示例：

> 用户："今天上午做了 API 配置，下午改了设备总览，然后开了个会。"

必须拆解为 3 项，而非当作 1 个任务：

```text
1. API 配置工作
2. 设备总览页面修改
3. 项目会议
```

输出模板见 `references/output-templates.md` 的「日复盘模板」。

## §2 MODE_DAILY_PLAN（今日计划）

执行 8 步：

```text
① 查今天任务        list_undone_tasks_by_time_query("today")
② 查逾期任务        list_undone_tasks_by_date(过去 14 天区间)
③ 查已有时间安排    filter_tasks(startDate/endDate 限定今日)
④ 识别重要事项      priority 5/3 + 用户上下文
⑤ 识别任务负荷      任务数量与预估耗时
⑥ 生成今日重点      最多 3 项
⑦ 给出延期建议      仅建议
⑧ 给出时间安排      含时间缓冲
```

**默认只给建议，不修改 TickTick 任务日期或优先级。** 仅当用户明确说「按你的计划帮我调整 TickTick」时，才允许执行调整，且每次调整需在同步清单中列出。

输出模板见 `references/output-templates.md` 的「今日计划模板」。

## §3 MODE_TASK_CLEANUP（任务整理）

执行 6 步：

```text
① 查看任务          全部项目 + 收集箱
② 识别模糊任务      "AI" / "API" / "看一下项目" 类
③ 识别重复任务      标题高度相似、同项目重复、已完成任务重复创建
④ 识别长期任务      长期未完成、多次延期、长期无更新、与当前项目失去关联
⑤ 识别未安排任务    无日期、无时间
⑥ 给出整理建议      每项任务只给「保留 / 拆分 / 延期 / 归档 / 删除」之一
```

默认**只报告，不删除、不大规模修改**。模糊任务的改写建议以「原任务 / 建议改写 / 原因」三列呈现。任务拆解同理：只建议，除非用户明确说「帮我拆成 TickTick 任务」。

输出模板见 `references/output-templates.md` 的「任务整理模板」。

### 任务系统健康度

用户说「检查一下我的 TickTick 健康度」时，分析并**仅输出问题清单**，不输出评分：

- 收集箱积压
- 未安排任务
- 长期未完成
- 多次延期
- 模糊任务
- 重复任务
- 当前任务负荷

输出形如：

```text
需要关注：
1. 长期未完成任务较多
2. 收集箱存在较多未整理事项
3. 部分任务描述过于模糊
```

**禁止输出「任务系统 85 分」之类缺乏明确意义的评分。**

## §4 MODE_PERIOD_REVIEW（周 / 月复盘）

执行 8 步：

```text
① 查本周完成      list_completed_tasks_by_date(周期区间)
② 查本周未完成    list_undone_tasks_by_date(周期区间)
③ 汇总实际工作    合并 TickTick 记录与用户补充口述
④ 按项目归类
⑤ 按工作类型归类
⑥ 分析时间投入
⑦ 找出延期事项
⑧ 输出下周关注事项
```

周复盘模板见 `references/output-templates.md` 的「周复盘模板」。

月度时间投入分析规则：

- **不得**由时间最多推导出「最重要」。只做事实陈述：「本月记录时间最多的项目是 A，共 X 小时。」
- 可同时给出投入与产出对照（时间 / 完成任务数 / 新增工作数 / 未完成数），但**不得**自动得出「投入产出低」的结论，除非用户明确要求进一步分析。
- 数据积累足够后，才做长期趋势分析：持续投入的项目、占比上升的工作类型、长期延期的任务、长期没有行动的目标。

## §5 MODE_NEXT_ACTION（下一步计划）

在复盘基础上识别「下一步行动」，默认**不创建新任务**。

示例：当前任务「完成 GPU 细粒度调度设计」，今日完成「MIG 模式设计」→ 判定原任务仍未完成，在复盘中指出「下一步仍需完成显存隔离、节点选择等部分」。

仅当用户说「帮我把下一步拆成 TickTick 任务」时，才执行创建。

输出「明日待处理」时按 优先 / 继续 / 可选 三档分组，且**不自动修改 TickTick**。

## §6 授权边界与透明反馈

### 自动允许（无需额外确认）

- 完成**明确完成**的已有任务（`complete_task`）
- 创建并完成**明确完成**的新工作（`create_task` + `complete_task`）
- 把本次记录到的**开始时间写入 `startDate`**
- 手动录入且明确的结束时间写入 `dueDate`；AI 推导的结束时间不写
- 只有存在**明确真实截止时间**时，才写入独立 `dueDate`
- 把 `taskId` **回写**到本地 WorkItem

完成判定的四个必要条件（缺一不可）：

```text
有明确任务 + 用户明确完成 + 实际工作覆盖任务范围 + 没有明显剩余工作
```

**「补写已发生的时刻」与「改计划安排」是两件事**：

- 自动做：把开始时间写 `startDate`，备注按 `content` 模板写（这是事实落位，不是改计划）。
- 先问用户：改变任务的计划日期、优先级、标题、清单归属。

实测依据（2026-09-21）：对 `status: 2` 的已完成任务写入 `startDate` / `isAllDay` 后，
`status` 与 `completedTime` 均不受影响 —— 补写历史开始时间安全、可逆。

### 默认不自动执行

- 删除任务
- 修改任务标题
- 修改日期
- 修改优先级
- 修改清单 / 项目归属
- 大量拆分任务
- 大规模重新规划

删除是**绝对红线**：永远不能仅凭 AI 判断直接删除用户任务，必须用户明确授权（如「把这些建议删除的任务直接删掉」）。

### 用户明确授权后（如「直接帮我整理 TickTick」）

可扩大操作范围至：识别模糊任务 → 改写 → 移动清单 → 设置优先级 → 安排日期。但每一步仍必须**不破坏原始信息**。

### 每次写操作后必须输出

```text
本次 TickTick 同步

完成原有任务：X
新增任务：X
更新任务：X
删除任务：0
未处理：X

事项 ↔ taskId 对照（供本地回写）：
- <事项名称>  → taskId: <taskId>  时间：<HH:MM-HH:MM 或 仅开始 / 未记录>
```

并列出具体任务。写操作为 0 时同样输出，注明「本次无写操作」。

**`taskId` 对照表是必须项**：本地日志不保存 TickTick ID，靠标题匹配存在改错风险。
每次同步都把「事项 ↔ taskId」明确列出，供 `work-time-tracking` 侧回写，之后即可按 id 精确定位。

### MCP 不可用时

必须如实报告，**禁止假装同步成功**：

```text
本次复盘已完成。

但 TickTick 当前无法连接，因此：
- 未完成自动同步
- 未创建新任务
- 未修改已有任务

以下为待同步内容：
...
```

## §7 最终原则

| # | 原则 |
|---|---|
| 01 | 真实完成优先于 TickTick 状态 |
| 02 | 部分完成不能标记整体完成 |
| 03 | 实际完成但没有任务 → 自动补录 |
| 04 | 补录前必须检查重复 |
| 05 | 小而有意义的工作可以记录 |
| 06 | 无实际价值的行为不创建任务 |
| 07 | 时间没有依据就不编造 |
| 08 | 删除操作默认不自动执行 |
| 09 | 大规模任务调整默认不自动执行 |
| 10 | 所有写操作必须透明反馈 |
| 11 | 复盘不是评价用户，而是记录事实 |
| 12 | TickTick 的目标不是「完成更多任务」，而是「准确反映真实工作」 |
| 13 | AI 推导事项只写 `startDate`；对话结束时间不得当真实结束时间或 `dueDate` |
| 14 | 手动明确录入的结束时间可写 `dueDate`；回读核对 `startDate` / `dueDate` / `isAllDay` / `timeZone` |
| 15 | 同步必须输出「事项 ↔ taskId」对照表，并回写本地以消除标题匹配风险 |
| 16 | 备注（`content`）只写 `content` 模板允许的内容：内部术语、TickTick 字段名、映射箭头、免责声明、模板外的自造行一律不写；写入前与回读后各校验一次 |

## §8 反模式（必须避免）

- **碎片任务污染**：不要为「打开文档 / 查看普通邮件 / 单纯查看页面 / 普通聊天 / 喝水」创建任务。记录「有工作意义的事件」，而不是记录所有行为。
- **任务数量膨胀**：补录遵循「工作事件优先，而非操作步骤」。用户说"做完设备总览页面"，只创建「完成设备总览页面设计」，**不要**创建「打开 Axure / 修改页面 / 修改表格 / 调整布局 / 保存原型」。
- **为增加完成数而拆分**：一项复杂工作（如「完成 GPU 细粒度调度设计」含 MIG、显存隔离、节点选择、调度策略）不应为了凑数量拆成 4 个「已完成任务」，除非这些本来就是独立工作。**不追求完成任务数量。**
- **虚构时间**：无数据来源时写「未记录」，不编造。
- **开始时间只写进备注**：把「11:30」只写进 `content` 就说时间已同步。开始时间必须落 `startDate`。
- **把对话结束时间当实际结束时间**：AI 推导事项的 `end_time` 只是会话收尾，不得写进 `dueDate`，也不得写进备注。
- **把实现细节写进备注**：`content` 里出现内部术语（`本地区间`、`本地时间线`）、TickTick 字段名（`startDate`）、映射箭头（`→`）、免责声明（`结束时间为会话收尾，非真实结束`）或模板之外的自造行。备注只写 `content` 模板允许的内容，写完必须校验。
- **全天态糊弄**：有时间段却仍用 `T00:00:00+0800` + `isAllDay: true`，等于没推时间。
- **为凑时间段造结束时间**：归类合并后无法确定结束时间时，保留开始时间、结束时间置空，不得用「开始 + 预估时长」编造。
- **只凭标题改任务**：标题搜索命中就直接 `update_task`，可能改错任务。必须核对 `content` 中的 `来源：WorkTimeLog WI-xxx` 或按 `taskId` 定位。
- **越权归类**：项目无法识别时不强行归类。

## §9 异常与边界处理

| 情形 | 处理 |
|---|---|
| 用户只说"复盘今天"未描述工作 | 先问「今天做了什么」，再进入判定 |
| 用户描述的任务在 TickTick 找不到 | 先 `search_task` 查重，确认无重复后再 `create_task` |
| 任务「部分完成」 | 不 `complete_task`；在复盘中列为部分完成并写明剩余部分 |
| 清单型任务仅完成部分子项 | 用 `update_task` 只把对应子项 `status` 置 1，**父任务保持未完成**；先 `get_task_in_project` 取最新 items 再整体回传（传 items 会重生成子项 id） |
| 用户口述的联系人不在子项清单中 | 先 `search_task` 查该联系人是否有独立历史任务；无法对应时**不擅自勾选**，向用户确认归属 |
| 任务已完成又出现在描述中 | ALREADY_COMPLETED，不重复操作 |
| 无法判断是否完成 | UNCERTAIN，不修改，列入「待确认」 |
| 用户口述跨多天工作 | 与用户确认归属日期后再落账 |
| 周期超过 14 天 | `list_undone_tasks_by_date` 单次上限 14 天，需分段查询后合并 |
| 查询工具校验失败 | 条件须包裹：`list_*_by_date` 用 `search` 键，`filter_tasks` 用 `filter` 键 |
| `create_task` 传 `status: 2` 不生效 | 已实测确认，改用「创建 → `complete_task`」两步法 |
| `list_completed_tasks_by_date` 返回空但任务确已完成 | 接口对本轮经 MCP 完成的任务存在索引延迟，改用 `list_undone_tasks_by_time_query` / `filter_tasks` 反向确认已移出待办 |
| AI 对话推导出时间段 | 只写 `startDate`；对话结束时间不写 `dueDate`，不宣称为实际结束 |
| 手动录入明确时间段 | `start_time` 写 `startDate`，`end_time` 写 `dueDate`，完整区间写 `content` |
| 只有开始时间没有结束时间 | 只写 `startDate`，`dueDate` 留空 |
| 归类合并后无法确定结束时间 | 保留开始时间；结束时间只按未知处理，输出时间列写 `15:20-` |
| 任务已完成，但要补写历史开始时间 | 安全：实测 `status` 与 `completedTime` 不受影响；写入后回读核对 |
| 任务已存在但标题与本地不一致 | 先回读 `content` 的 `来源：WorkTimeLog WI-xxx` 核对；有 `taskId` 优先按 id 定位。**宁可不动，不可改错** |
| 时间字段写入后回读不一致 | 重新 `update_task` 并显式传 `isAllDay: false`；仍不一致则列入「待处理」，不得宣称同步成功 |
| 回读发现 `content` 不符模板（多出模板外的行 / 含内部术语、字段名、免责声明 / 缺 `来源：WorkTimeLog <id>` 锚点） | 用 `scripts/validate-content.js` 复现违规项，再 `update_task` **只改 `content`**（不碰 `status` 与时间字段），重写后回读核对；无法重写则列入「备注待修正」，不得宣称同步成功 |

## 完成判定的五种状态

| 状态 | 含义 | 操作 |
|---|---|---|
| FULLY_COMPLETED | 完整完成 | 自动完成 |
| PARTIALLY_COMPLETED | 部分完成 | 不完成 |
| NEW_COMPLETED_WORK | 新增并完成 | 创建 + 完成 |
| UNCERTAIN | 无法判断 | 不修改 |
| ALREADY_COMPLETED | 已经完成 | 不操作 |
